title: Merge Gate
oneLiner: A policy check that keeps a red pull request out of main.
stack:
  - GitHub Actions
  - TypeScript
  - SQLite
updatedAt: "2026-09-24"
claim: >-
  A pull request that fails the policy check cannot merge: the 2026-09-24 seeded
  fixture blocked 1 of 1 red pull requests and let 0 red pull requests reach
  main.
problem: >-
  Branch protection listed the policy job as advisory. A maintainer could merge
  a red pull request after the job reported failure, and the failure could edit
  its own rules file in the same change.
constraint: >-
  GitHub Actions only, with no third-party app and no server. The gate had to
  fetch the pull request diff, evaluate a stored rule set, and post a required
  check run.
architecture: >-
  The workflow triggers on pull_request, fetches the head SHA and diff through
  the API, loads rules from SQLite, evaluates each rule, and posts a check run
  named policy-gate. Branch protection requires that check on main.
decisions:
  - title: Required check, not a comment
    choice: >-
      Configure policy-gate as a required status check in branch protection.
    rejected: >-
      A bot comment that a maintainer can ignore. In the 2026-09-12 trial, 2 of
      5 red pull requests merged after a comment-only run.
    cost: >-
      The repository owner must grant admin rights to edit branch protection,
      and every merge waits for the check to finish.
    evidence: >-
      The seeded red pull request returns a failing check run, and main receives
      0 merge commits.
  - title: Rules stored in SQLite, not in the pull request
    choice: >-
      Load policy rules from a SQLite database owned by the platform team.
    rejected: >-
      Rules in a YAML file inside the repository. A red pull request could edit
      the rule that judges it, and the gate would read the edited copy.
    cost: >-
      A rule change needs a migration and a platform review, so a team cannot
      ship a rule in the same pull request as its code.
    evidence: >-
      The force-push fixture changes the repository YAML and the stored rules
      still return the original verdict.
  - title: Fail closed on timeout
    choice: >-
      Return a failing check when the gate cannot finish inside its timeout.
    rejected: >-
      Fail open on timeout. A slow runner would report success and let a red
      pull request through.
    cost: >-
      A runner outage blocks all merges until the check is rerun; the block is
      visible but expensive.
    evidence: >-
      The timeout fixture returns a failing conclusion and main stays unchanged.
failures:
  - date: "2026-08-29"
    commit: "b7d9e10"
    summary: >-
      Commit b7d9e10 read the head SHA from the event payload. After a

      old diff and reported green on a red head.
    processChange: >-
      The workflow now fetches the head SHA through the API at check time,
      asserts it matches the event, and the seed includes a force-push case.
